# GithubHot 接入 PoW（工作量证明）防御调研报告

> 调研日期：2026-10-08 ｜ 范围：现状盘点 + 业界方案对比 + 接入路线建议
> 前提约束：不改动任何项目代码；不绕过现有反指纹/风控体系

---

## 一、现状盘点：本站已建成一套自研 PoW，处于"影子模式"

调研的第一个、也是最重要的结论：**GithubHot 不需要"从零接入"PoW——P4-3 已经把全链路建成了，目前只是默认关闭（`ALTCHA_DIFFICULTY=0` 影子模式）**。打开它是一个纯运维动作（配置环境变量），不涉及代码改动。

### 已在库的完整链路

| 组件 | 位置 | 状态 |
|---|---|---|
| 服务端签发/校验（纯函数域包） | `internal/domain/altcha/altcha.go` | ✅ 完整，含单测 |
| 挑战端点 `GET /api/v1/altcha/challenge?fp=` | `internal/interfaces/httpapi/altcha.go` | ✅ 常开 |
| 执行挂钩（fp/report 强制校验） | `fp_report.go` | ✅ 已挂，仅 `altchaEnforced()` 时生效 |
| 前端求解器（WebCrypto） | `web/src/lib/altcha.js` → `solveAltcha(fp)` | ✅ 已接入上报流程（`fingerprint.js` 上报时自动带解） |
| APP 参考实现（同算法） | `altcha.Solve()` 镜像函数 | ✅ |

### 自研实现的设计亮点（比朴素 hashcash 强的四点）

1. **无状态签发**：`challenge = base64url(过期时间戳:难度:salt:HMAC)`，服务端签发后不存任何状态，校验时重算 HMAC 即可——刷挑战端点本身没有存储放大面。
2. **绝对过期时间戳防重放**：解只有 10 分钟（`ALTCHA_MAXAGE_SEC` 默认 600s）有效期，过期即废。
3. **挑战绑定设备指纹（关键）**：签发时服务端计算 `HMAC(challenge|fp|ghID)`，校验时与请求声明的指纹比对——**一份算好的解无法换一台设备重放**。这使 PoW 的"人格证明"锚定在指纹体系上，天然满足"不绕过指纹层"的红线。
4. **难度封在 HMAC 里**：客户端无法自降难度。

### 为什么默认关闭

灰度纪律（规格书 P4-3）：先影子模式观察求解耗时分布，确认真实用户无感后再转强制。这个决策是正确的，报告第 5 节给出演进路线。

## 二、PoW 防御的适用边界（诚实评估）

### 有效场景

- **接口刷量**：fp/report、搜索、内容接口被脚本批量调用——PoW 把每次请求的客户端成本从 ≈0 提到毫秒~秒级 CPU，规模化攻击的成本随请求数**线性放大**，服务器端校验成本却近乎为零（一次 SHA-256 + HMAC）。
- **批量伪造设备**：指纹可以伪造，但每台伪造设备都要烧 CPU 求解，农场规模越大越贵。
- **IPv6/代理池场景**：IP 限频对海量 IPv6 伪造失效，而 PoW 按"计算成本"计费，与 IP 无关——是这一场景下少数有效的公平手段。
- **爬虫抓站**：配合指纹白名单（搜索引擎豁免）可以有选择性拦截。

### 无效/受限场景（必须有预期）

- **确定性定向攻击**：攻击者写 GPU/分布式求解器。PoW 挡的是"概率性滥用"（多数廉价脚本），不挡决心烧钱的对手——后者需要的是内存难算法（Argon2id，见路线 C）和风控纵深。
- **真人肉鸡**：代理池里的真浏览器有真 CPU，PoW 照样能解。
- **流量型 DDoS**：PoW 是 CPU 层手段，流量层要靠 CDN/云防火墙（另一条战线）。
- **弱设备体验**：老旧手机解高难度会明显发热变慢——难度必须按最弱目标设备设定（见第 5 节参数表）。
- **电池成本（APP 端）**：移动端频繁求解会耗电，难度与求解频率是两根必须一起管的旋钮。

## 三、业界方案对比（2026 年现状调研）

### 3.1 Anubis（TecharoHQ）——"AI 爬虫防火墙"，反代形态

- **机制**：反向代理层，访客先过 PoW 挑战再放行到源站；可配置 bot 策略白名单（放行搜索引擎/Internet Archive 等）。
- **现状**：MIT 协议，23.2k stars，非常活跃（944 commits）；GNOME、GitLab 生态、kernel.org 等"小互联网"阵营广泛采用，用于对抗 2024 起的 AI 训练爬虫潮。
- **形态**：Go 单二进制，nginx 前置反代；也有发行版打包。
- **适配本站的得/失**：
  - 得：成熟免维护、社区对抗经验活跃、保护整站（含网页静态资源）。
  - 失：它面向**网页浏览**——APP 的 API 客户端（无 JS 求解环境）必须按路径豁免，否则直接弄坏 APP；等于网站前多一层独立组件与两套并行体系；网页首屏增加 1–3 秒挑战时间。

### 3.2 ALTCHA（官方版，altcha-org）——本站自研实现的"同宗官方版"

- **机制**：Web Component + 服务端校验库（**官方有 Go 库**），默认 PBKDF2/SHA-256，**支持 Argon2id / Scrypt 内存难算法**（抗 GPU/ASIC 农场）；MIT；宣称 GDPR/无 Cookie/WCAG 无障碍合规。
- **体量**：34KB gzipped（对比 reCAPTCHA ~300KB、Turnstile 85KB+）。
- **适配本站**：算法契约与自研版同源（HMAC 挑战 + 前导零）。若未来攻击者升级到 GPU 求解，**可以把自研的 SHA-256 难题换成 Argon2id 内存难题**——接口形态不变，属平滑升级。

### 3.3 mCaptcha——自适应难度的独立服务

- **机制**：Rust 自托管服务；SHA-256 PoW + **按流量压力自适应难度**（官方口径：平时无感，攻击时升到 ~2 秒）；解一次性、~30 秒过期、与 IP 无关（NAT 友好）。
- **许可**：AGPL-3.0（对自用无碍，二次分发需注意传染性）。
- **适配本站**：要多跑一个独立服务（Docker 可用），且它的"票"模型（客户端→mCaptcha 验票→业务端再验票）与本站"挑战绑定指纹"的模型不同，接入需要改 fp/report 协议——**性价比低于打开已有 ALTCHA**。
- **值得借鉴**：自适应难度曲线（见第 5 节）。

### 3.4 Cloudflare Turnstile——托管验证（非 PoW）

- 免费、隐形模式、验证码体验最好；但是**第三方依赖**：验证 iframe 与脚本来自 challenges.cloudflare.com，境内可达性波动；隐私声明/合规负担；对 APP 内嵌 WebView 的兼容要单独验证。
- **结论：不推荐**。本站核心诉求（接口防刷）用已有 PoW 足够，无需引第三方进信任链。

### 3.5 结论对比表

| 方案 | 形态 | 新依赖 | 对 APP 通道 | 与指纹层配合 | 适配评级 |
|---|---|---|---|---|---|
| **自研 ALTCHA（已有）** | 应用内挂钩 | **零** | 同算法已备 | 挑战绑指纹，原生契合 | ★★★★★ 推荐立即启用 |
| Anubis 反代 | 独立反代 | 一个组件 | 需路径豁免 | 两套体系并存，需梳理 | ★★☆ 仅网页被抓站时补挂 |
| ALTCHA 官方库 | 算法替换 | Go 库 | 同 | 同 | ★★★☆ 未来抗 GPU 升级路径 |
| mCaptcha | 独立服务 | 一个服务 | 改协议 | 需重构挂钩 | ★★ 不推荐 |
| Turnstile | 托管第三方 | 外部依赖 | WebView 兼容存疑 | 第三方进信任链 | ★ 不推荐 |

## 四、接入路线（按推荐排序）

### 路线 A（推荐）：打开已有的 ALTCHA——纯运维动作，零代码

三档灰度：

| 档位 | 配置 | 效果 |
|---|---|---|
| 影子模式（现状） | `ALTCHA_DIFFICULTY=0` | 端点在线、上报带解但不强制——**现在就是这个状态，可先积累求解耗时数据** |
| 常规强制 | 服务器 `.env`：`ALTCHA_SECRET=<32B 随机>`、`ALTCHA_DIFFICULTY=14`、重启 | fp/report 无有效解 → 记录并扣分（进入指纹积分体系），脚本成本 ×16k |
| 高压模式 | 攻击期间临时 `ALTCHA_DIFFICULTY=18` + 收紧 `ALTCHA_MAXAGE_SEC=120` | 求解秒级，批量脚本基本失效 |

操作要点：`ALTCHA_SECRET` 用 32 字节随机值（服务器上 `head -c 32 /dev/urandom | base64` 生成，写入 `.env` 同 APP_SIGN_SEED 流程）；难度升级只改数字重启。

### 路线 B：Anubis 反代层——只在"网页被抓站"成为实际问题时启用

- 挂点：服务器 nginx(443) → Anubis → 应用 8787，**只挂网页路径**；`/api/v1/*`（APP 签名通道）与 `/video/*` 保持直连，由本站指纹 + ALTCHA 负责。
- 启用时机信号：日志出现明显 AI 爬虫 UA/抓取行为、带宽被静态资源爬走。
- 与指纹层的关系：Anubis 在前拦截浏览器爬虫，本站指纹体系在后管 API 与 APP——**两层各管一段，互不替代**；APP 与已通过指纹的网页会话应加白名单避免双重摩擦。

### 路线 C：算法升级预备（抗 GPU 农场）

若观察到攻击者用 GPU 求解 SHA-256（特征：求解耗时异常稳定且快），下一步是换**内存难算法**：把自研挑战的哈希函数从 SHA-256 换成 Argon2id（官方 ALTCHA 库的 Go 实现可参考）。内存难算法让 GPU/ASIC 无优势，每解一题都要占真实内存带宽。接口形态不变，属平滑替换。

### 不推荐

- Turnstile（第三方依赖 + 境内可达性 + 隐私链路）。
- mCaptcha（独立服务 + 票模型重构，收益不抵复杂度）。

## 五、难度参数速查（SHA-256，JS WebCrypto 单线程量级估算）

| 难度（前导零比特） | 平均哈希次数 | 桌面 JS | 中端手机 JS | 用途 |
|---|---|---|---|---|
| 12 | ~4,096 | ~20ms | ~50ms | 影子/极轻 |
| 14 | ~16k | ~0.1–0.3s | ~0.3–0.6s | **建议默认档** |
| 16 | ~65k | ~0.5–1.3s | ~1.5–3s | 高压档 |
| 18 | ~262k | ~2–5s | ~6–12s | 攻击期档 |
| 20 | ~1M | ~8–20s | ~25–50s | 紧急档（真用户会抱怨） |

参数建议：`ALTCHA_DIFFICULTY=14` 起步、`ALTCHA_MAXAGE_SEC=600`（默认）；APP 端（原生代码）求解比 JS 快 5–20 倍，同难度无感。

**进阶方向（需小改代码，本次不动）**：自适应难度——用 IPGuard 现有的设备积分调难度：低分（可信）设备发 12 比特轻挑战、高分（可疑）设备发 18+ 比特重挑战。真用户无感，可疑流量成本翻倍。这是 PoW 与反指纹体系联动的最佳形态，mCaptcha 的核心卖点本站架构天然支持。

## 六、与反指纹体系的配合（红线确认）

1. **挑战在指纹核验后签发**：`challenge?fp=` 绑定指纹签发，解不可跨设备重放——已实现，这是"PoW 不绕过指纹层"的结构性保证。
2. **PoW 失败是证据不是裁决**：无有效解 → 记录事件进积分体系（与其他信号互证），不直接封禁。
3. **影子模式先行**：转强制前积累真实求解耗时分布，确保最弱的真实用户设备也能在 1 秒内完成。
4. **APP 与网页同源同算法**：客户端求解逻辑已在域包中镜像实现，APP 发版时可直接接入（当前 APP 未强制）。

## 七、结论

1. **本站不需要"接入"PoW——它已经建成，只差拨开关**。唯一的实际动作是把 `ALTCHA_SECRET`（32B 随机）与 `ALTCHA_DIFFICULTY=14` 写入服务器 `.env` 并重启，建议先影子观察一周再转强制。
2. 业界对比结论：自研实现的设计（无状态、绑指纹、防重放）与主流方案同代，**无需替换**；Anubis 仅作为"网页被抓站"场景下的补充层；Argon2id 内存难模式是抗 GPU 升级的预留路径。
3. 全程零代码改动、零新依赖，指纹层红线（挑战绑指纹、失败只计分不裁决）在现有设计中原生满足。
